# تصميم الأساس التشغيلي لنظام إدارة الدراسات العليا

**الحالة:** معتمد للتنفيذ  
**النطاق الأول:** كلية الطب - جامعة أسيوط  
**الفرع:** `enterprise-development`

## 1. الهدف

بناء نظام تشغيلي ناجح لإدارة الدراسات العليا بكلية الطب - جامعة أسيوط، على أساس هندسي قابل للتحديث والتوسع مستقبلًا. لا تشمل المرحلة الحالية منصة متعددة الجامعات؛ تُحفظ فقط العلاقات الأساسية للجامعة والكلية حتى لا يلزم إعادة بناء قاعدة البيانات لاحقًا.

## 2. المبادئ المعتمدة

1. التشغيل الأول لطب أسيوط فقط.
2. الاعتمادات الرسمية ورقية وليست إلكترونية.
3. النظام يتابع حركة المعاملة ويسجل نتيجة الاعتماد الورقي، ولا يصدر قرارًا أو توقيعًا إلكترونيًا.
4. يمكن رفع PDF أو صورة للمستند الورقي، مع بقاء الورق هو الأصل الرسمي.
5. الطالب يرى وينزل مستنداته فقط.
6. الموظف يرى السجلات الواقعة داخل دوره ونطاق القسم أو البرنامج المسند إليه.
7. مدير برنامج الدراسات العليا يمتلك صلاحيات تشغيلية كاملة على مستوى الكلية.
8. جميع عمليات العرض والتنزيل والرفع والتعديل وتغيير الصلاحيات تُسجل.
9. المستندات لا تُحذف نهائيًا؛ تُؤرشف وتُحفظ إصداراتها السابقة.
10. أسماء الجامعة والكلية والمسؤولين وإعدادات الإجراءات تُحفظ في البيانات ولا تُثبت داخل الكود.

## 3. المعمارية

- Backend: Django + Django REST Framework + PostgreSQL.
- Web: React.
- Mobile: Expo/React Native.
- API بإصدارات تبدأ من `/api/v1/`.
- تطبيقات مستقلة وظيفيًا: accounts, academics, students, documents, workflows, theses, committees, audit.
- نماذج University وFaculty موجودة من البداية، دون تنفيذ Multi-Tenancy كامل في النسخة الأولى.
- كل خدمة حساسة تطبق التفويض في الخادم، لا في الواجهة فقط.

## 4. الأدوار والصلاحيات

يصبح `User.roles` المصدر النهائي للأدوار. يبقى `User.role` مؤقتًا للتوافق، وتُنقل بياناته عبر data migration قبل حذفه في إصدار لاحق.

قرار الوصول يعتمد على:
- الدور والصلاحية.
- نطاق الكلية والقسم والبرنامج.
- ملكية السجل للطالب.
- حالة المعاملة عند الحاجة.

مدير البرنامج يرى ويدير جميع بيانات كلية الطب، مع تسجيل كل إجراء. مسؤول النظام التقني لا يحصل تلقائيًا على حق قراءة المستندات الحساسة.

## 5. المستندات الورقية

يحفظ StudentDocument نوع المستند وصاحبه ورقم المستند وتاريخه وجهة الاعتماد وتاريخ الاعتماد الورقي وحالته والملف وإصداره وبصمته الرقمية ورافعه وأوقات الإنشاء والتعديل والأرشفة.

قواعد الملفات:
- لا توجد روابط عامة للوسائط.
- التنزيل عبر endpoint محمي أو رابط مؤقت.
- التحقق من الملكية والنطاق لكل طلب.
- السماح بـPDF والصور الموثوقة ضمن حد حجم محدد.
- التحقق من النوع الحقيقي وحساب SHA-256.
- الاستبدال ينشئ DocumentVersion ولا يمحو النسخة القديمة.
- تسجيل العرض والتنزيل والرفع والاستبدال.
- يظهر تنبيه أن التسجيل داخل النظام لا يمثل اعتمادًا إلكترونيًا.

## 6. متابعة الإجراءات الورقية

المسار التشغيلي: إنشاء الطلب، استكمال البيانات، تقديم الورق، تسجيل انتقال الملف، تسجيل نتيجة الجهة بعد صدورها ورقيًا، إدخال رقم القرار وتاريخه، رفع النسخة الممسوحة، إظهار الحالة المناسبة للطالب، ثم الأرشفة.

لا تستخدم الواجهة عبارات مثل "اعتماد إلكتروني". تستخدم: "تسجيل الموافقة الورقية"، "إثبات صدور القرار"، و"تحديث حالة المستند".

## 7. الأمان

- كلمات مرور قوية، منع المحاولات المتكررة، وMFA للحسابات الإدارية.
- Access tokens قصيرة العمر مع تدوير وإلغاء refresh tokens.
- عدم تخزين رموز جلسة الويب النهائية في localStorage.
- HTTPS وsecure HttpOnly cookies عند اعتماد تدفق الويب.
- حماية CSRF وXSS وCSP وClickjacking.
- تدقيق رفع الملفات وفحصها.
- سجل تدقيق غير قابل للتعديل من المستخدمين.
- تشفير النسخ الاحتياطية واختبار الاستعادة.
- منع الأسرار والبيانات الحقيقية من المستودع، وتحويله إلى Private قبل استخدامها.
- الالتزام بقانون حماية البيانات الشخصية المصري رقم 151 لسنة 2020.

## 8. معالجة الأخطاء

- استجابات API موحدة دون كشف تفاصيل داخلية.
- رفض العمليات غير المصرح بها بـ403 دون تسريب وجود السجل.
- المعاملات المركبة داخل database transactions.
- منع التكرار بقيود قاعدة البيانات.
- optimistic locking أو version fields للسجلات الحساسة.
- حفظ سبب العمليات الإدارية الحساسة.

## 9. الاختبارات

- migrations قابلة للتطبيق على قاعدة فارغة.
- اختبارات ملكية مستندات الطالب ومنع IDOR.
- اختبارات عزل الأقسام وصلاحيات المدير.
- اختبارات رفع وتنزيل وإصدارات الملفات.
- اختبارات سجل التدقيق.
- اختبارات المصادقة والقفل وانتهاء الجلسات.
- اختبارات إجراءات الاعتماد الورقي.
- هدف تغطية لا يقل عن 85% للمنطق الحساس.
- فحوصات Django وRuff والاختبارات وفحص الاعتماديات ضمن CI.

## 10. ترتيب التنفيذ

1. إنشاء migrations المفقودة واختبار قاعدة فارغة.
2. إزالة غموض role/roles عبر migration انتقالية.
3. تثبيت المؤسسة والبرامج ونطاق المستخدم.
4. بناء طبقة التفويض وسجل التدقيق.
5. بناء المستندات والتنزيل الآمن.
6. بناء بوابة الطالب للمستندات.
7. بناء متابعة الموافقات الورقية.
8. استكمال ملف الطالب والرسائل واللجان والتقارير.
9. استكمال الويب والموبايل.
10. اختبارات الأمان والأداء والنسخ الاحتياطي.
11. تشغيل تجريبي محدود، معالجة الملاحظات، ثم إطلاق طب أسيوط.

## 11. معايير القبول

- الطالب لا يصل إلا إلى بياناته ومستنداته.
- الموظف لا يتجاوز نطاقه.
- المدير يمتلك صلاحيات الكلية الكاملة مع audit trail.
- لا يوجد اعتماد إلكتروني ضمن النسخة الحالية.
- لا يوجد ملف حساس عام أو حذف نهائي غير مقصود.
- قاعدة جديدة تُبنى وتُرحل دون أخطاء.
- الاختبارات والأمان والنسخ الاحتياطي والاستعادة ناجحة.
- الواجهات العربية والإنجليزية تعمل، والعربية هي الافتراضية.

## 12. خارج النطاق الحالي

Multi-Tenancy الكامل، التوقيع والاعتماد الإلكتروني، اشتراكات الجامعات، الربط القومي، ولوائح جميع الجامعات. تظل أهدافًا مستقبلية تُبنى بعد نجاح التشغيل الفعلي في طب أسيوط.
