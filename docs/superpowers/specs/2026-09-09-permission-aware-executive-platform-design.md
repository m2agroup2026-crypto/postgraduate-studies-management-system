# تصميم منصة الصلاحيات ومركز القيادة الأكاديمي التنفيذي

**التاريخ:** 2026-09-09  
**الفرع:** `feature/academic-history-platform-foundation`  
**نقطة البداية:** `0de4109`  
**الحالة:** معتمد للتنفيذ

## 1. الهدف

إنشاء أساس دائم للصلاحيات يفصل إدارة المنصة عن المناصب الأكاديمية، ويقدم للأستاذ الدكتور محمد عبد الباسط خلاف، وكيل الكلية لشئون الدراسات العليا والبحوث، مركز قيادة أكاديمي تنفيذي Premium يعتمد على بيانات API الحقيقية فقط.

## 2. قاعدة الملكية والإدارة

- حساب `Ahmed` هو الحساب الوحيد الذي يجمع دوري `PLATFORM_ADMIN` و`PROGRAM_DIRECTOR`.
- حساب `Ahmed` هو الوحيد الذي يحصل على صلاحيات إعدادات المنصة وإدارة الأدوار والصلاحيات.
- لا يكتسب العميد أو وكيل الكلية أو أي منصب أكاديمي صلاحيات إدارة المنصة بسبب منصبه.
- يظل `User.role` مدعومًا خلال المرحلة الانتقالية، بينما تصبح `User.roles` المصدر الدائم للأدوار المتعددة.

## 3. Namespace الصلاحيات

الصيغة القياسية تستخدم أسماء الموارد بالجمع:

- `students.view`, `students.create`, `students.update`, `students.manage`
- `theses.view`, `theses.create`, `theses.update`, `theses.manage`
- `committees.view`, `committees.create`, `committees.update`, `committees.manage`
- `reports.view`, `reports.export`
- `dashboard.manage`, `roles.manage`, `permissions.manage`, `users.manage`

تدعم الصيغ القديمة مثل `thesis.view` و`committee.approve` عبر Alias Mapping مركزي مؤقت. لا تُخزن الصيغ القديمة كصلاحيات جديدة، وتبقى الاختبارات القديمة صالحة خلال الانتقال.

## 4. المصفوفة المعتمدة

### Ahmed — مدير المنصة والبرنامج

- الأدوار: `PLATFORM_ADMIN`, `PROGRAM_DIRECTOR`.
- يملك جميع صلاحيات تكوين المنصة والمستخدمين والأدوار والصلاحيات.
- يملك صلاحيات البرنامج التشغيلية الكاملة المطلوبة للإضافة والتعديل والمتابعة.

### VICE_DEAN_POSTGRADUATE

يمثل الأستاذ الدكتور محمد عبد الباسط خلاف – وكيل الكلية لشئون الدراسات العليا والبحوث.

- عرض الطلاب: `students.view`.
- عرض الرسائل العلمية: `theses.view`.
- عرض اللجان والمناقشات: `committees.view`.
- عرض التقارير ومتابعة الاعتمادات التي تدخل ضمن مرحلته الفعلية.
- لا يحصل على `dashboard.manage`, `roles.manage`, `permissions.manage`, `users.manage`.
- لا يحصل على `students.manage`, `theses.manage`, `committees.manage` إلا إذا أضيف احتياج Workflow معتمد في تصميم لاحق.

### المناصب الأخرى

تمنح أقل صلاحية لازمة للوظيفة. لا يحصل `DEAN` أو `VP_POSTGRADUATE_RESEARCH` أو غيرهما على صلاحيات تكوين المنصة تلقائيًا.

## 5. البذر الدائم

- ينشئ `seed_roles` الصلاحيات القياسية ويحدث أسماءها وحالتها بصورة متكررة وآمنة.
- يعيد ربط كل دور بالمصفوفة المعتمدة باستخدام `set` لمنع تراكم صلاحيات قديمة.
- ينشئ أو يحدث حساب `Ahmed` من `seed_demo` ويربطه دائمًا بالدورين الإداري والبرنامجي.
- يربط حساب `vice_dean` بدور `VICE_DEAN_POSTGRADUATE` فقط.
- لا توضع كلمة مرور ثابتة في الكود؛ تستخدم `PGMS_DEMO_PASSWORD` أو آلية إعداد آمنة مماثلة.

## 6. التفويض وواجهات API

- كل Endpoint يتحقق من الصلاحية القياسية المطلوبة في Backend.
- إخفاء عناصر الواجهة ليس بديلًا عن حماية API.
- يعيد `/me/` قائمة الصلاحيات الفعالة والأدوار الفعالة وخصائص إدارة المنصة.
- يعيد Dashboard وحدات التنقل وQuick Actions بعد ترشيحها حسب صلاحيات المستخدم.
- محاولة فتح إعدادات المنصة دون `dashboard.manage` تعيد `403`.

## 7. مركز قيادة وكيل الكلية

- يستخدم شعار كلية الطب الموجود.
- يعرض اسم وصفة الوكيل بصورة دقيقة.
- يعرض KPIs مشتقة من قاعدة البيانات فقط: الطلاب، الرسائل حسب الحالة، اللجان، المناقشات القادمة، والطلبات التي تنتظر مرحلته.
- لا يستخدم أرقامًا ثابتة أو بيانات تجريبية داخل مكونات React.
- يعرض وحدات الطلاب والرسائل واللجان فقط إذا كانت صلاحيات العرض متاحة.
- لا يعرض الإعدادات أو إدارة المستخدمين أو الصلاحيات للوكيل.

## 8. التوجه البصري

- هوية تنفيذية أكاديمية مستمدة من كلية الطب: كحلي عميق، أزرق مؤسسي، أخضر طبي هادئ، أبيض دافئ، وذهبي محدود للتأكيد.
- RTL عربي أصيل، وتدرج بصري واضح للمعلومات التنفيذية.
- Lucide Icons مرتبطة بوظائف حقيقية وليست زخرفية.
- الحركة تقتصر على انتقال دخول منظم، hover/focus دقيق، واستجابة المساعد.
- تعطّل الحركة غير الضرورية عند `prefers-reduced-motion: reduce`.
- التصميم Responsive لسطح المكتب والتابلت والموبايل مع لوحة تنقل قابلة للاستخدام بلوحة المفاتيح.

## 9. المساعد الذكي

- يظهر كزر Floating Premium دون تغطية محتوى مهم.
- يحصل على Quick Actions من بيانات مسموح بها للمستخدم.
- كل Quick Action إما ينقل إلى وحدة متاحة فعليًا أو يرسل طلب API فعليًا.
- لا تظهر Actions لوحدات غير مصرح بها، ولا توجد أزرار Placeholder.
- تبقى إجابات المساعد مقيدة ببيانات وصلاحيات المستخدم.

## 10. الاختبارات وبوابات القبول

- اختبارات Backend لمصفوفة الصلاحيات، aliases، idempotent seed، حساب `Ahmed`، وحساب الوكيل.
- اختبارات API لضمان ظهور الوحدات المسموحة ورفض إعدادات المنصة.
- اختبار عدم تسرب إدارة المنصة إلى الأدوار الأكاديمية.
- نجاح جميع اختبارات Backend دون Regression.
- نجاح Frontend production build.
- عدم وجود أرقام KPI ثابتة في الواجهة.
- مراجعة بصرية Desktop وMobile بعد اكتمال التنفيذ.
- commits واضحة وpush إلى الفرع المحدد فقط، دون Merge.

## 11. خارج النطاق

- لا Merge إلى `enterprise-development` أو `main`.
- لا بناء محرر Workflow مرئي كامل ضمن هذه الدفعة.
- لا منح صلاحيات إدارة المنصة لأي حساب غير `Ahmed`.
- لا إضافة بيانات وهمية لتحسين مظهر Dashboard.
- لا كسر للـAPI أو الاختبارات القديمة دون طبقة توافق موثقة.
